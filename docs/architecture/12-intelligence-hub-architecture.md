# 12 — Intelligence Hub Architecture

## Purpose

This document describes the architecture of the Intelligence Hub — the system that allows users to read, edit, and understand everything an agent "knows": its persona, memory, and skills. It covers the storage model, API design, context loading, compact algorithm, and the Cockpit UI data flow.

**Reference:** For full design requirements, see `docs/agent-subagent-design-requirements.md`.

---

## Agent Memory Storage Model

All agent memory lives in object storage (MinIO/S3) under the user's prefix. The Intelligence Hub exposes this via a REST API; it does not introduce a separate database.

```
{user_id}/agents/{agent_id}/
├── profile.md                                   ← agent persona (read/write)
├── manifest.json                                ← capabilities, tool hint (managed by create_agent)
├── config.json                                  ← LLM, skills, MCP (managed by create_agent)
└── memory/
    ├── working/
    │   ├── context.md                           ← ACTIVE scratchpad (read/write)
    │   └── archive/
    │       └── {date}-compact-{label}.md        ← compacted snapshots (read-only)
    ├── episodic/
    │   ├── {date}-compact-{label}.md            ← ACTIVE session archives (read-only, loaded into context)
    │   └── archive/
    │       └── {date}-compact-{label}.md        ← ARCHIVED sessions (read-only, never loaded)
    └── semantic/
        ├── knowledge.md                         ← default knowledge file (always provisioned)
        └── {topic}.md                           ← additional user-authored topics
```

**System agents** (`system/agents/{agent_id}/`) have `profile.md`, `manifest.json`, `config.json` only. No memory subfolder — system agents are stateless.

## API Routes (`api/intelligence.py`)

All routes are prefixed `/app/v1/intelligence/` and require Bearer JWT auth.

### Agent List

```
GET  /intelligence/agents
```
Scans MinIO `{user_id}/agents/` prefix, reads each `manifest.json`, returns:
```json
[{ "agent_id": "research-agent", "name": "Research Agent", "source": "user" }]
```
Also includes system agents accessible to the user.  
**Purpose:** Intelligence Hub agent selector — NOT the canvas API.

### Agent Profile

```
GET  /intelligence/agents/{agent_id}/profile    → { agent_id, content, updated_at }
PUT  /intelligence/agents/{agent_id}/profile    body: { content }
```

### Working Memory

```
GET  /intelligence/agents/{agent_id}/memory/working          → { agent_id, memory_type, key, content }
PUT  /intelligence/agents/{agent_id}/memory/working          body: { content }
GET  /intelligence/agents/{agent_id}/memory/working/archive  → [{ name, size_chars, created_at }]
POST /intelligence/agents/{agent_id}/memory/compact          body: { summary, session_label? }
                                                             → CompactResponse
```

`CompactResponse`:
```json
{
  "agent_id": "research-agent",
  "archived_as": "2026-04-20-compact-sprint-12.md",
  "working_context_replaced": true,
  "context_before_chars": 12450,
  "context_after_chars": 387,
  "reduction_pct": 96.9
}
```

### Episodic Memory

```
GET    /intelligence/agents/{agent_id}/memory/episodic
       → [{ name, content, created_at, status: "active" | "archived" }]

GET    /intelligence/agents/{agent_id}/memory/episodic/{name}
       → { agent_id, name, content, status }

POST   /intelligence/agents/{agent_id}/memory/episodic/{name}/archive
       → { archived_to: "episodic/archive/{name}" }
       (irreversible — moves from episodic/ to episodic/archive/)
```

> Delete endpoint removed in favour of archive. Episodic entries are never deleted — only archived.

### Semantic Memory

```
GET    /intelligence/agents/{agent_id}/memory/semantic
       → [{ topic, content, updated_at }]

GET    /intelligence/agents/{agent_id}/memory/semantic/{topic}
       → { agent_id, memory_type, key, content }

PUT    /intelligence/agents/{agent_id}/memory/semantic/{topic}   body: { content }
       (creates if not exists — PUT is both create and update)

DELETE /intelligence/agents/{agent_id}/memory/semantic/{topic}
```

### Skill Authoring

```
GET    /intelligence/skills/authored
POST   /intelligence/skills/authored                body: { name, description?, version?, content }
GET    /intelligence/skills/authored/{skill_id}
PUT    /intelligence/skills/authored/{skill_id}     body: { content, name?, description?, version? }
DELETE /intelligence/skills/authored/{skill_id}
POST   /intelligence/skills/authored/{skill_id}/fork  body: { name? }
POST   /intelligence/skills/validate                body: { content }
POST   /intelligence/skills/import                  multipart: file=<SKILL.md>
```

## Compact Operation — Algorithm

```
POST /intelligence/agents/{agent_id}/memory/compact
Body: { summary: str, session_label?: str }
```

**Steps:**
1. Read `working/context.md` → `original_content`; measure `context_before_chars`
2. Generate entry name: `{today}-compact-{slugify(session_label) or uuid4().hex[:8]}.md`
3. Build archive document:
   ```markdown
   # Compacted Context — {today}
   *Session: {session_label}*

   ## Original Working Context
   {original_content}
   ```
4. Write archive document to:
   - `episodic/{entry_name}` — new **active** episodic entry (loaded into sub-agent context)
   - `working/archive/{entry_name}` — working memory snapshot (read-only archive, not loaded)
5. Replace `working/context.md` with `summary`
6. Return `CompactResponse` with `archived_as`, before/after char counts, reduction %

## Context Loading in SubAgentRunner

`SubAgentRunner._build_system_prompt()` assembles the sub-agent's execution context in this order:

```
1. Agent profile.md
2. ## Working Context  ←  memory/working/context.md
3. ## Episodic Memory  ←  ALL files in memory/episodic/ (NOT episodic/archive/)
                          newest first; truncate oldest if over budget
4. ## Semantic Knowledge  ← ALL files in memory/semantic/
                            knowledge.md first; rest alphabetical
```

**Token budget guard:** 80,000 tokens default. Truncation order (removed first): oldest episodic → alphabetically-last semantic → working context never truncated.

**Implementation note:** As of Phase 5, only steps 1–2 are implemented. Steps 3–4 are required backend changes (B5 in the implementation plan).

## Intelligence Hub Cockpit UI

The Cockpit Intelligence Hub (`src/features/intelligence/`) exposes all memory tiers via the selected agent. Each tab maps to a memory type:

| Tab | Data Source | Editable |
|---|---|---|
| Agent Profile | `GET/PUT .../profile` | ✅ |
| Working Memory | `GET/PUT .../memory/working` + archive list | ✅ active; read-only archives |
| Episodic Memory | `GET .../memory/episodic` (active + archived with status) | ❌ read-only; archive action |
| Semantic Memory | `GET/PUT/DELETE .../memory/semantic/*` | ✅ full CRUD |
| Skill Authoring | `GET/POST/PUT/DELETE/fork/validate .../skills/authored/*` | ✅ full CRUD |

**Agent selector:** Uses `GET /app/v1/intelligence/agents` (MinIO scan) — not the canvas definitions API.

│  Working Files       │  context.md  (3,241 chars)            │

## Multi-Tenant Isolation

All memory paths are scoped to `{user_id}/agents/{agent_id}/`. The API enforces isolation by injecting the authenticated `user_id` from the JWT — users can never access another user's agent memory, even if they know the path structure.

The path is never constructed client-side. The UI sends only `agent_id`; the backend resolves the full MinIO path via `StoragePaths`.
