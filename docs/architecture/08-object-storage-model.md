# 08 — Object Storage Data Model

## Purpose

This document defines the complete data model for object storage (MinIO in local development, AWS S3 in production).  It answers three questions that were previously unclear in the architecture:

1. **What** is persisted to object storage and why (vs. PostgreSQL or Redis)
2. **Where** each object lives — the full bucket path convention
3. **When** objects are created, updated, and deleted

---

## Storage vs. Database Decision Table

| Data Type | Store | Rationale |
|---|---|---|
| Task graph, goals, resources, edges | PostgreSQL + AGE | Relational/graph queries, ACID transactions, joins |
| Scoring history, state transitions | PostgreSQL | Time-series queries, audit trail |
| Skill .md definitions, agent profiles, memory | Object Storage | Large Markdown blobs, user-editable, schema-free |
| User app settings, scoring weights | Object Storage | JSON blobs, user-owned, rarely queried |
| Inbound message attachments | Object Storage | Binary files, arbitrary size |
| Pub/sub events, queue state | Redis | Ephemeral, high-throughput, not durable |
| LLM API keys, channel credentials | Secrets Manager | Never in DB or object storage |

---

## Multi-Tenant Isolation Model

The bucket root is partitioned by `user_id` so that IAM / MinIO bucket policies can grant each authenticated user access to **only** their own `{user_id}/` prefix.  No user-specific data ever lives outside this prefix.

```
{bucket}/
├── system/             ← shared read-only data (no user data)
└── {user_id}/          ← ALL user data lives here (RBAC boundary)
```

**RBAC policy (per-user):**

```json
{
  "Effect": "Allow",
  "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject", "s3:ListBucket"],
  "Resource": [
    "arn:aws:s3:::{bucket}/{user_id}/*"
  ],
  "Condition": {
    "StringEquals": { "s3:prefix": "{user_id}/" }
  }
}
```

System skills are readable by all users but writable only by admin principals.

## Complete Bucket Layout

All paths are generated by `StoragePaths` in [src/graphclaw/infra/storage.py](../../src/graphclaw/infra/storage.py).  **No code may construct storage path strings by hand** — always call the appropriate `StoragePaths` method.

```
{bucket}/
│
├── system/
│   └── skills/
│       └── definitions/
│           └── {skill_name}/
│               └── SKILL.md                        ← built-in skill (seeded once at boot)
│
└── {user_id}/
    ├── config.json                                  ← user app settings (LLM, timezone, channels)
    ├── scoring_weights.json                         ← 7-factor weight overrides (W1–W7)
    │
    ├── agents/
    │   └── {agent_id}/
    │       ├── profile.md                           ← agent persona, goals, working style
    │       ├── config.json                          ← agent operational config (heartbeat, LLM)
    │       └── memory/
    │           ├── working/
    │           │   └── context.md                   ← current-session scratchpad (overwritten each cycle)
    │           ├── episodic/
    │           │   └── {YYYY-MM-DD}-{session}.md    ← archived session summaries (append-only)
    │           └── semantic/
    │               └── {topic}.md                   ← long-term factual knowledge by topic
    │
    ├── skills/
    │   ├── registry/
    │   │   ├── sources.json                         ← registered remote skill sources
    │   │   └── installed.json                       ← installed skill metadata + quality scores
    │   ├── cache/
    │   │   └── {source_hash8}/{skill_name}/SKILL.md ← downloaded remote skills (cached)
    │   ├── authored/
    │   │   └── {skill_id}/SKILL.md                  ← user-authored / forked skill definitions
    │   └── executions/
    │       └── {skill_id}.json                      ← skill execution history
    │
    └── attachments/
        └── {channel}/{YYYY-MM-DD}/{msg_id}/{file}   ← inbound message attachments
```

## Object Lifecycle

### System Skill Definitions

| Event | Action |
|---|---|
| Application first boot | `minio-init` or app startup seeder writes each built-in SKILL.md to `system/skills/definitions/{name}/SKILL.md` — only if the object does not already exist (`exists()` guard) |
| Skill definition update | Admin deploys new version; seeder does NOT overwrite (user must explicitly update via API) |
| Never deleted | System skills are permanent; they are the canonical fallback |

> **Design intent:** The `src/graphclaw/skills/definitions/` folder in source code is **seed data only**.  It is never read at runtime after the first boot.  All runtime reads go through object storage.

### User Config (`config.json`, `scoring_weights.json`)

| Event | Action |
|---|---|
| First API call with no config | `FileNotFoundError` is caught; defaults are returned without writing |
| `PATCH /app/v1/settings` | Current config is loaded, patched in-memory, then written back |
| `PATCH /app/v1/settings/scoring-weights` | Same pattern |
| User account deletion (GDPR) | `delete` called on `{user_id}/` prefix — all objects removed |

### Agent Profile and Memory

| Event | Action |
|---|---|
| `PUT /intelligence/agents/{id}/profile` | Written unconditionally |
| Agent loop cycle start | Agent reads `working/context.md`; on `FileNotFoundError` starts with empty context |
| Agent loop cycle end | Agent overwrites `working/context.md` with updated context |
| Session end / context too large | `/compact` endpoint archives current `working/context.md` to `episodic/{date}-{session}.md`, replaces working context with compact summary |
| User edits memory via cockpit | `PUT` on the relevant memory endpoint |
| User deletes memory via cockpit | `DELETE` on the relevant memory endpoint |

**Episodic memory** accumulates over time (append-only for system writes, user can delete individually).  **Semantic memory** topics are updated in-place.  **Working memory** is a volatile scratchpad overwritten every cycle.

### Skill Registry

| Event | Action |
|---|---|
| `POST /skills/sources` | Source URI registered in `{user_id}/skills/registry/sources.json` |
| `POST /skills/install` | SKILL.md downloaded from remote, cached at `{user_id}/skills/cache/{hash}/{name}/SKILL.md`; metadata appended to `installed.json` |
| `DELETE /skills/{id}` | Cached SKILL.md deleted; entry removed from `installed.json` |
| Skill source removed | All installed skills from that source are uninstalled |

### Authored Skills

| Event | Action |
|---|---|
| `POST /intelligence/skills/authored` | New SKILL.md written to `{user_id}/skills/authored/{skill_id}/SKILL.md` |
| `PUT /intelligence/skills/authored/{id}` | SKILL.md overwritten |
| `POST /intelligence/skills/authored/{id}/fork` | Source SKILL.md copied to new `{fork_id}/SKILL.md` |
| `DELETE /intelligence/skills/authored/{id}` | SKILL.md deleted |
| Authored skill install | Cockpit calls `POST /skills/install` with `source_uri="local://authored"` — the registry service reads from `authored/` prefix |

### Attachments

| Event | Action |
|---|---|
| Inbound message with attachment | `AttachmentHandler.process()` downloads from channel CDN and writes to `{user_id}/attachments/{channel}/{date}/{msg_id}/{unique}_{filename}` |
| Never automatically deleted | Attachments are durable; lifecycle policies (e.g. S3 expiry after 90 days) should be configured at the infrastructure level |

## Intelligence Hub API

The `GET /app/v1/intelligence/...` endpoints expose the agent memory and skill authoring features to the cockpit UI.  Full endpoint list:

```
# Agent profile
GET    /app/v1/intelligence/agents/{agent_id}/profile
PUT    /app/v1/intelligence/agents/{agent_id}/profile

# Working context
GET    /app/v1/intelligence/agents/{agent_id}/memory/working
PUT    /app/v1/intelligence/agents/{agent_id}/memory/working
POST   /app/v1/intelligence/agents/{agent_id}/memory/compact

# Episodic memory
GET    /app/v1/intelligence/agents/{agent_id}/memory/episodic
GET    /app/v1/intelligence/agents/{agent_id}/memory/episodic/{entry_name}
DELETE /app/v1/intelligence/agents/{agent_id}/memory/episodic/{entry_name}

# Semantic memory
GET    /app/v1/intelligence/agents/{agent_id}/memory/semantic
GET    /app/v1/intelligence/agents/{agent_id}/memory/semantic/{topic}
PUT    /app/v1/intelligence/agents/{agent_id}/memory/semantic/{topic}
DELETE /app/v1/intelligence/agents/{agent_id}/memory/semantic/{topic}

# Skill authoring
GET    /app/v1/intelligence/skills/authored
POST   /app/v1/intelligence/skills/authored
GET    /app/v1/intelligence/skills/authored/{skill_id}
PUT    /app/v1/intelligence/skills/authored/{skill_id}
DELETE /app/v1/intelligence/skills/authored/{skill_id}
POST   /app/v1/intelligence/skills/authored/{skill_id}/fork
POST   /app/v1/intelligence/skills/validate
POST   /app/v1/intelligence/skills/import
```

## CLI Commands

The `graphclaw intelligence` sub-command group provides direct object-storage access for development and debugging without the cockpit UI.

```bash
# Requires these env vars:
export GRAPHCLAW_USER_ID=your-user-id
export STORAGE_BUCKET=graphclaw
export STORAGE_ENDPOINT_URL=http://localhost:9000   # MinIO
export AWS_ACCESS_KEY_ID=graphclaw
export AWS_SECRET_ACCESS_KEY=graphclaw_dev

# Inspect all paths for your user
graphclaw intelligence skill paths

# Profile
graphclaw intelligence profile show
graphclaw intelligence profile set profile.md

# Working context
graphclaw intelligence memory working show
graphclaw intelligence memory working set context.md
graphclaw intelligence memory working compact --summary "Brief summary of session"

# Episodic memory
graphclaw intelligence memory episodic list
graphclaw intelligence memory episodic show 2026-04-11-compact-abc123.md

# Semantic memory
graphclaw intelligence memory semantic list
graphclaw intelligence memory semantic show users

# Skill authoring
graphclaw intelligence skill list
graphclaw intelligence skill validate my-skill/SKILL.md
graphclaw intelligence skill create my-skill/SKILL.md
graphclaw intelligence skill show my-authored-skill
```

## Code Cleanup Notes

The following path string literals were removed and replaced with `StoragePaths` calls:

| File | Old Path | New Via StoragePaths |
|---|---|---|
| `api/settings.py` | `agents/{user_id}/config.json` | `StoragePaths.user_config(user_id)` |
| `api/settings.py` | `agents/{user_id}/scoring_weights.json` | `StoragePaths.user_scoring_weights(user_id)` |
| `skills/registry.py` | `skills/registry/{user_id}/sources.json` | `StoragePaths.skill_registry_sources(user_id)` |
| `skills/registry.py` | `skills/registry/{user_id}/installed.json` | `StoragePaths.skill_registry_installed(user_id)` |
| `skills/registry.py` | `skills/cache/{user_id}/{hash}/{name}/SKILL.md` | `StoragePaths.skill_cache(user_id, hash8, name)` |
| `api/skill_registry.py` | `skills/executions/{user_id}/{skill_id}.json` | `StoragePaths.skill_executions(user_id, skill_id)` |
| `gateway/attachment_handler.py` | `attachments/{channel}/{date}/{msg_id}/...` | `StoragePaths.attachment(user_id, ...)` |

The `AttachmentHandler.process()` and `process_all()` signatures now require a `user_id` parameter to enforce the per-user storage prefix.
